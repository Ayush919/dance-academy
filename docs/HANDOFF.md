## 1. What this is

A premium public website **plus** a complete business system for a multi-branch dance academy. The demo brand is **Remo Dance Company** (Mumbai and Pune); every brand detail is editable from the dashboard, so the same software can serve any academy.

From one dashboard the academy runs: its website (pages, menus, branding, SEO, media), branches and rooms, programs, fee plans, instructors, batches and the timetable, families and students, consent forms and documents, enrolment with seat holds and a waitlist, and (planned) attendance, fees and payments, CRM, marketing, notifications and reports.

**Who uses it**

| Person | What they do |
|---|---|
| Visitor / parent | Browses programs and classes, books a trial, contacts the academy, shares a story. |
| Guardian | Manages their children, signs forms, uploads documents, enrols in classes, joins the waitlist, accepts seat offers. |
| Adult student | Same as a guardian, for themselves. |
| Teen student (13+) | Optional view-only login (**not built yet**; permissions exist). |
| Instructor | Sees their batches and students (instructor portal is Phase 8). |
| Receptionist | Handles walk-ins, enrolments, enquiries at their branch. |
| Branch manager | Runs one branch. |
| Academy admin | Runs the academy and the website. |
| Super admin | Everything. |

**Business decisions already made (do not re-ask)**
- Hosting: **Vercel free plan** plus an external scheduler (GitHub Actions or cron-job.org) for frequent jobs.
- Billing: **monthly, in advance on the 1st, prorated** for mid-month joins, **not GST-registered** (GST can be switched on in settings later, no code change).
- Logins: guardians manage children under 18; students aged 13+ may get an optional **view-only** login; adults manage themselves.
- Database: **MongoDB Atlas, Mumbai (`ap-south-1`)**; local development uses a single-node replica set.
- **No payment gateway.** Payments are recorded manually (cash, UPI, bank transfer, card POS, cheque). Razorpay is planned later; the data model reserves room for it.
- All money is stored in **paise** (integer). All times are stored in **UTC**; schedules are defined in the **branch's local time**.

## 3. Run it on this Mac

Requirements: Node 22+, MongoDB 6+ binaries (`brew install mongodb-community`).

```bash
cd /Users/ayushmathur/personal-projects/dance-academy
npm install
npm run db:dev            # single-node replica set on port 27018, data in ./.data (git-ignored)
cp .env.example .env.local   # then fill it in (below)
npm run seed              # demo academy, branches, catalogue, content, consent forms
npm run dev               # http://localhost:3000   (health: /api/health)
```

`.env.local` (never committed; `.env*` is git-ignored except `.env.example`):

| Variable | Needed | Notes |
|---|---|---|
| `APP_URL` | yes | `http://localhost:3000` locally. Also used for the same-origin checks. |
| `ACADEMY_SLUG` | yes | Which academy this deployment serves (`remo` in the seed). |
| `MONGODB_URI` | yes | Local: `mongodb://127.0.0.1:27018/remo?replicaSet=rs0`. Must be a replica set (transactions). |
| `BETTER_AUTH_SECRET` | yes | `openssl rand -base64 48` |
| `CRON_SECRET` | yes | `openssl rand -hex 32`; bearer token for `/api/cron/*` |
| `REQUIRE_EMAIL_VERIFICATION` | no | `false` locally |
| `SEED_ADMIN_EMAIL`, `SEED_ADMIN_PASSWORD`, `SEED_ADMIN_NAME` | yes for seed | Creates the super admin. Password 12+ characters. `owner@remodance.example` was used locally. |
| `SEED_GUARDIAN_EMAIL`, `SEED_GUARDIAN_PASSWORD` | optional | A local demo parent. The seed does **not** create it; sign it up at `/register`. |
| `SEED_ALLOW_REMOTE` | no | Seed refuses a non-local DB unless `true`. |
| `RESEND_API_KEY`, `EMAIL_FROM` | production | Without them, emails are written to the server log. |
| `CLOUDINARY_CLOUD_NAME/API_KEY/API_SECRET` | production | Without them, uploads go to `public/uploads` (dev only) and documents to `.data/private`. |
| `GOOGLE_MAPS_API_KEY`, `TURNSTILE_SECRET_KEY` | optional | |

**A new machine/account does not have `.env.local` or the local database.** Recreate both with the steps above. The database starts empty; `npm run seed` rebuilds the demo.

**Commands**

| Command | What it does |
|---|---|
| `npm run typecheck` | `next typegen` then strict `tsc` (run this, not bare `tsc`: route types are generated) |
| `npm run lint` | ESLint. 2 known React Compiler *warnings* (React Hook Form `watch`, TanStack Table) are expected; **0 errors** is the bar. |
| `npm test` | Vitest: unit + integration (starts an in-memory replica set). Faster: `TEST_MONGODB_URI="mongodb://127.0.0.1:27018/?replicaSet=rs0" npm test` |
| `npm run build` | Production build |
| `npm run format` | Prettier |
| `npm run db:dev` / `db:stop` | Start / stop the local replica set |
| `npm run seed` | Idempotent demo data |

If the dev server holds stale model definitions after changing a Mongoose schema, restart it. If a schema change alters an index, drop the stale index in the dev database (the seed will complain "An existing index has the same name…").

## 4. How to use the application

### 4.1 Public website (`/`)
Home, About, Programs (+ detail), Classes (every open batch with **live seats left**, price, "Enrol now" or "Join waitlist", "Book a trial", "Enquire"), Instructors (+ profile), Events (+ detail), Gallery, Contact (form, studios, FAQ), Book a trial, **Share your story** (public review form; reviews wait for approval), and any CMS page (`/privacy`, `/terms`, `/refund-policy`, plus pages the studio creates). Header, footer, announcement bar, colours and fonts all come from the CMS. `/sitemap.xml`, `/robots.txt`, share images and structured data are generated.

### 4.2 Parent / family portal (`/portal`) — sign up at `/register`, sign in at `/login`
- **Family home:** each dancer, their classes, waitlist places, seat offers with a countdown, and a to-do list (forms to sign, documents expiring).
- **Add a dancer** (or "I'm the dancer" for adults): name, date of birth, emergency contacts, health notes.
- **Dancer page:** classes, **forms** (read, type your name, tick, sign; media release lets you choose website / social / print / video; withdraw any time), **documents** (private upload), details.
- **Enrol** (`/portal/enrol/<batchId>`, from "Enrol now" on any class): shows eligibility, forms to sign, documents needed, fee plan choice, an optional 15-minute seat hold, and **Confirm enrolment** (everything is re-checked at that instant). If the class is full: **Join the waitlist**; when a seat opens the family gets an email and has 24 hours to accept.
- **Family details:** family name, billing details, preferred contact channel.

### 4.3 Studio dashboard (`/admin`) — sign in as staff
Sidebar groups and what they do:

| Area | Pages |
|---|---|
| Overview | **Dashboard** (live numbers). |
| Academy | **Branches & rooms** (hours, facilities, rooms, closures, holidays), **Programs**, **Fee plans** (versioned prices), **Instructors**, **Batches** (conflict-checked schedules), **Timetable** (week view, move/cancel sessions). |
| People | **Students**, **Families**, **Enrolments** (list; per-batch **roster and waitlist**), **Consent forms**. |
| Website | **Website** (pages, navigation, brand, SEO), **Media library**, **Gallery**, **Testimonials**, **Redirects**. |

Common tasks:
- **Create a walk-in family:** Families → New family → add dancers → (later) link the parent by their sign-up email.
- **Enrol a student:** Enrolments → *Enrol a student* (or a student's page → *Enrol in a batch*). The same checks as families; the studio can override level and missing documents (never forms or capacity).
- **Record a paper signature:** student page → Forms → *Read and sign* (marked "recorded by the studio").
- **Manage a waitlist:** Enrolments → batch → Waitlist: change order (needs a reason) or remove.
- **Edit the website:** Website → pick a page → section builder with autosave, live preview at phone/tablet/desktop, **Publish** (blocked until valid), **Schedule**, **History** (restore), **Take offline**. Navigation/Brand/SEO edit the same way.
- **Publish a photo of a child:** Gallery → tag the dancer. Publishing is refused unless that family has a current media release; withdrawing the release hides the item automatically.
- **Change a consent form's wording:** Consent forms → edit. Saves a **new version** and families are asked to sign again.

### 4.4 Roles and permissions
Central policy in `src/server/rbac/policy.ts` (permission × role → scope: `all`, `branch`, `assigned`, `own`). Every service starts with `authorize(...)`; lists use `scopeFilter` / `peopleFilter`. Branch managers/receptionists see their branches' data (plus new sign-ups with no branch yet); instructors see their batches and their students; guardians see only their household; students see only themselves.

### 4.5 Scheduled jobs
`POST /api/cron/<job>` with `Authorization: Bearer $CRON_SECRET`. Idempotent; safe to run late or twice.
`generate-sessions` (daily) · `reconcile-seats` (daily) · `publish-scheduled` (every 10 min) · `waitlist-offers` (every 10 min). Production: `vercel.json` (daily backstops) and `.github/workflows/cron.yml` (every 10 minutes; needs repository secrets `APP_URL`, `CRON_SECRET`). Locally call them with `curl`.

## 7. How the code is organised

```
src/
  app/            Routes. (site) public · (auth) · admin · portal · api
  components/     site/ (Stage), admin/ (Studio), families/ (portal + staff families UI),
                  forms/ (field kit), ui/ (shadcn), states/, motion/
  content/        CMS schema (src/content/schema.ts), seed copy, defaults
  lib/            Client-safe helpers (money, phone, slug, youtube, use-now, auth-client)
  server/
    actions/      Server Actions (thin: validate, call ONE service, return {ok, data|error})
    auth/         Better Auth config, session → Actor, auth emails
    context/      Request context, page helpers (withRequestContext, requireStaff/Member)
    db/           connect, transaction, tenant plugin, model helpers, all() (no parallel ops in a txn)
    domain/       PURE rules: schedule.ts, enrolment.ts, enums.ts (client-safe)
    integrations/ email (Resend/log), media-store (Cloudinary/local), private-store (documents)
    jobs/         Scheduled jobs
    lib/          errors, result, boundary (defineAction/defineRoute), rate-limit, pagination, file-sniff…
    models/       Mongoose schemas (all registered in models/index.ts)
    rbac/         policy.ts (the permission matrix), authorize.ts
    services/     ALL business rules. Start with authorize(), transactions for multi-writes, audit every change.
    validators/   Zod schemas shared by forms (client) and services (server)
scripts/          seed.ts, seed-catalogue.ts, seed-consents.ts
tests/            unit/ + integration/ (against a real replica set) + support/
docs/             SPEC, ARCHITECTURE, DATABASE, SETUP, CHECKLIST, HANDOFF (this), PLAN (superseded)
```

**Rules the code follows**
1. UI never touches models; it calls Server Actions or service functions.
2. Boundaries (`defineAction`, `defineRoute`) build the context, validate with Zod, call **one** service, return `{ ok, data } | { ok: false, error: {code, message, fields?, details?} }`.
3. Services do the permission check first, run multi-document writes in `withTransaction`, write an audit entry for every mutation, and throw `AppError` for expected failures.
4. Domain functions are pure and unit-tested; no I/O, no clock reads (callers pass `now`).
5. Every tenant-owned model uses the tenant plugin; queries without a request context throw. Aggregates are auto-filtered.
6. Money = integer paise. Times = UTC; dates that are calendar facts (birthdays, batch start) are `"YYYY-MM-DD"` strings.
7. Financial and consent records are **append-only**; corrections are new records.
8. Public data is cached with `'use cache'` + tags; mutations call `updateTag` (actions) or `revalidateTag(tag,'max')` (jobs/routes).

## 10. Gotchas (learned the hard way)

- **No parallel operations inside a MongoDB transaction.** Use `all()` from `src/server/db/concurrent.ts`, not `Promise.all`.
- **Forms send raw input** (see §8).
- **Models must be registered** before `populate`; `models/index.ts` is imported by the connection.
- **Request-context store lives on `globalThis`** (Next can load a module once per bundle).
- **Aggregates are already tenant-filtered**: don't add an `academyId` match with a string id; it matches nothing.
- **Mongoose adds `updatedAt` to every update.** Any pre-update hook that whitelists fields must allow it (the consent guard does).
- **React Compiler lint:** don't call setState from an effect, even through a helper. Load in event handlers, or on the server and pass props.
- **Cache Components keeps the previous route mounted** after navigating; close dialogs before `router.push`.
- **dnd-kit needs `id={useId()}` on `DndContext`** or hydration mismatches appear.
- **Aggregates/`lean()` skip virtuals; `select: false` fields** (student `medicalNotes`) are only returned with `.select('+medicalNotes')` after a permission check.
- **Don't re-add `revalidateTag` next to `updateTag`** in actions; one is enough.
- **Prettier may reformat code mid-edit**, so exact-string edits can miss; re-read the file.
- **Radix `Select` rejects empty-string item values**; give it a placeholder instead.
- **Stale dev state:** restart `npm run dev` after schema changes; drop renamed indexes in the dev DB.
